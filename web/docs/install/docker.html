Docker

One image, built by this repository's CI from the same commit as the release binaries, published to GitHub's registry:

$ docker run --rm -e WALLET=4YourAddress… -e POOL=gulf.moneroocean.stream:10001 \
    ghcr.io/molik-labs/zmrig

No installation, no compiler, no dependencies. docker inspect on a running container answers with the commit that built it.

TagWhat it is
ghcr.io/molik-labs/zmrig:6.48.0one release, and it never changes
ghcr.io/molik-labs/zmrig:latestthe newest release
ghcr.io/molik-labs/zmrig:edgethe tip of BETA — for testing, not for a rig you care about

Check the wallet before anything else​

A rig that mines to an address it cannot be paid at is the most expensive mistake in this project, because it looks exactly like a working rig. The image answers that question with no pool, no config and no boot:

$ docker run --rm -e WALLET=4YourAddress… ghcr.io/molik-labs/zmrig check
valid   4YourAddress…
  check checksum verified (Keccak-256)
  kind  standard
  net   mainnet

A typo is refused, and says which check failed:

$ docker run --rm -e WALLET=4YourAddress…f ghcr.io/molik-labs/zmrig check
invalid 4YourAddress…f
  checksum does not match: at least one character is wrong

A typo is refused, and the same check runs again at startup, from the miner itself, so the verdict is in the log of every container whether or not anyone asked for it.

What to set​

The variable names are the ones zmrig-os writes to /etc/zmrig/os.conf, so a rig that came from the appliance and a rig that came from this image are configured with the same vocabulary.

VariableDefaultWhat it does
WALLET—the address this rig is paid to. Required
POOL—host:port, or tls://, ws://, wss://
WORKERxthe worker name. Many rigs on one wallet aggregate into one balance
MODEmaxmax (full speed), eco (most hashrate per watt), safe (adds the thermal governor), light (256 MiB)
ALGOautorx/0, rx/wow, … or auto, which lets the pool switch the rig between RandomX variants
THREADSautocache-aware, and capped by a CPU quota (below)
DONATE3the developer fee, in percent. 0 turns it off
SAFE_TEMP72the ceiling MODE=safe never crosses, in °C
MSRautoon, off, auto; safe never writes a register
API_PORT0the miner's monitoring API; 0 is off
API_HOST0.0.0.0its bind address when API_PORT is set — a loopback bind is unreachable from outside a container
API_TOKEN—require Authorization: Bearer T on that API
EXTRA_ARGS—more miner flags, split on whitespace and never passed through a shell

docker run --rm -e WALLET=… -e POOL=… ghcr.io/molik-labs/zmrig args prints the command line it would run and exits — the answer to "why is it using four threads when this machine has eight".

The full table, including the two variables that exist for tests, is doc/DOCKER.md.

Two optimisations that matter in a container​

A CPU quota is not an affinity mask. docker run --cpus=2 limits the group, but the process still sees every CPU on the host, so a miner that sizes itself from the CPU count asks for one thread per core and then shares two cores' worth of time. That is slower than two threads at full speed: when the quota is spent the whole group stops, and a thread with a dataset page in cache sits idle for the rest of the period. The image reads the cgroup quota and, when THREADS=auto, caps the thread count to it:

$ docker run --rm --cpus=2 -e WALLET=… -e POOL=… ghcr.io/molik-labs/zmrig args
zmrig: the container is limited to 2 CPUs (16 visible): 2 mining threads
/usr/local/bin/zmrig -o pool.example:3333 -u 4… -p x -t 2 --profile free …

--cpuset-cpus needs none of this: the kernel hides the other CPUs and the miner sizes itself correctly.

The fee is on the command line. --donate-level 3 is always passed explicitly, so the number a rig pays is visible in args instead of being a default inside a binary. Three percent is the default; DONATE=0 turns it off and the build fails its own tests if the code and the documentation disagree.

What a container cannot do​

Huge pages are reserved by the kernel at boot, MSR writes need /dev/cpu/*/msr, and thermal sensors are not namespaced. The image says so instead of failing quietly:

  • Huge pages need --cap-add=IPC_LOCK and a /dev/hugepages mount, on top of the host reserving them (sysctl vm.nr_hugepages, or zmrig-os hugepages).
  • MSR writes (MSR=on) let a container poke CPU registers; MSR=auto leaves it to the miner's probe, which will say no.
  • MODE=safe reads the host's sensors, which is what you want — and why the governor belongs on the host when the host runs more than one container.

Updating​

An image is replaced, never patched in place:

$ ./zmrig-docker-update --check     # 0 current, 3 available, 2 cannot tell
$ ./zmrig-docker-update --apply     # pull, then recreate — only if there is something new

--check runs the checker inside the image already on disk: it resolves the published tag over anonymous HTTPS and compares the release label with the version baked into the running container. No Docker socket in the container, no node on the host. --apply pulls first and recreates second, because a failed pull must leave the running miner alone.

Both halves, the compose file and a daily systemd timer are in deploy/docker/. The timer treats "an update was installed" (3) as success and "the registry could not be reached" (2) as a notice — a miner must not be restarted because GitHub was briefly unreachable, and a unit that goes red on every blip is a unit that gets masked.

Pinning is the other option and a good one: ghcr.io/molik-labs/zmrig:6.48.0 never changes, so a nightly compose pull is a no-op until you edit the file.

The pool, from the same image​

$ docker run -d --name pool -p 3333:3333 -p 8080:8080 \
    -e DAEMON=http://your-node:18081 \
    -e OPERATOR_ADDRESS=4YourAddress… \
    -v pool-data:/app/pool/data \
    ghcr.io/molik-labs/zmrig pool

A rig and the pool it mines to are then never built from different commits. The pool's own settings are in running a pool.
