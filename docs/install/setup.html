Setup from zero

This page is the decision, not the reference. It assumes one thing: you have a Monero address and a machine with a CPU. Pick a route, run one command, then run the five checks in Did it work. Everything else on this page is what you will want on day two.

RouteBest forWhat it touchesTime
A. One commanda machine you own and keepinstalls a service, writes /etc/zmrig/config.json5–10 min, mostly compiling
B. Containera server, a NAS, Kubernetes, anything already running containersnothing outside the container1 min
C. Bootable imagea dedicated rig, or a machine you do not want to install anything ona USB stick, or the rig's own disk5 min

All three run the same miner and the same hash engine. The difference is what happens to the host.

First, the wallet​

Wrong wallet, no payout — and a Monero address is 95 characters with a checksum, so a typo is silent until the pool refuses it. Check it before it goes into a config:

zmrig --check-wallet 4YourMoneroAddress

It prints the kind, the network, and the spend and view keys, or the exact reason it is not usable. If you have not built the miner yet, the container does it for you:

docker run --rm -e WALLET=4YourMoneroAddress ghcr.io/molik-labs/zmrig check

The installer and the appliance run the same check before they write anything, so a bad address fails at setup rather than at the first payout.

A. One command​

curl -fsSL https://raw.githubusercontent.com/MoLik-Labs/ZMRIG/BETA/oneclick.sh \
  | sudo bash -s -- --wallet 4YourMoneroAddress

From a clone, sudo ./oneclick.sh --wallet 4YourMoneroAddress is the same thing. The installer builds, measures the machine to pick a thread count, tunes the host, writes the config, installs zmrig.service, and prints the hashrate it measured.

Before it touches anything, ask it what it would do:

./oneclick.sh plan

The flags worth knowing on day one:

FlagWhy
--pool HOST:PORTthe pool; a short name such as supportxmr also works
--rig-id NAMEwhat this machine is called on the pool dashboard
--profile free|wattmaximum hashrate, or maximum hashrate per watt
--max-temp 70shed threads as the CPU warms instead of cooking it
--donate-level 3the developer fee, 0..10; 0 turns it off

The rest are in every installer option.

B. Container​

One command, no build, no service on the host:

docker run -d --name zmrig --restart unless-stopped \
  -e WALLET=4YourMoneroAddress \
  -e POOL=gulf.moneroocean.stream:10001 \
  -e WORKER=rig-01 \
  ghcr.io/molik-labs/zmrig

The container reads the same names the appliance writes to /etc/zmrig/os.conf, so MODE, THREADS, DONATE, SAFE_TEMP, MSR, API_PORT and EXTRA_ARGS all work. Two of them matter on a shared server:

  • --cpus=2 is a quota, not a core count. The container reads its own cgroup limit and caps the thread count to it, because a quota spread over too many threads is slower than fewer threads at full speed.
  • API_PORT=18080 switches the monitoring API on, and it binds to loopback inside the container — publish it deliberately, -p 127.0.0.1:18080:18080.

When the log says the rig mines fewer threads than the host has cores, ask the container what it actually told the miner:

docker run --rm -e WALLET=4YourMoneroAddress ghcr.io/molik-labs/zmrig args

Every variable is in the container reference.

C. The bootable image​

A rig that only mines does not need a general-purpose distribution. The image is a kernel, a read-only Alpine root with zmrig and its control tool, and nothing else running:

# the manifest for your CPU level, then the ISO it names
curl -fsSLO https://github.com/MoLik-Labs/ZMRIG/releases/download/os-beta/zmrig-os-beta-x86-64-v3.json

# write it to a stick — the ISO comes from the releases page
sudo dd if=zmrig-os-<version>-x86-64-v3.iso of=/dev/sdX bs=4M status=progress conv=fsync

Boot the rig, answer the wallet question, and it hashes. Nothing is written to the machine, so one stick can set up a hundred machines.

A rig with a disk of its own is better off installed, and the same image does it:

zmrig-os install --disk /dev/nvme0n1   # partition, copy, boot from the disk

Both forms are configured by hand-free one-liners when there is no keyboard:

zmrig-os setup --wallet 4YourMoneroAddress --pool gulf.moneroocean.stream:10001 --mode max

The image, its modes and its persistence rules are in the appliance manual.

Did it work​

Five checks, in this order. Each one answers a different question, and the first three take ten seconds.

CheckCommandWhat a good answer looks like
Is it running?sudo ./oneclick.sh statusa service in active, a hashrate that climbs past warming up
Does the hash engine match its reference vectors?sudo ./oneclick.sh verifyPASS lines, then verified
Is the fee what the docs say?sudo ./oneclick.sh verifyfee audit: one wallet, Monero only, switchable off
Is this rig laid out correctly?zmrig-os doctorevery line ok; anything else names the machine, not the symptom
How fast is it, really?zmrig --bench=20000 or zmrig-os bencha number in H/s, measured, comparable with the benchmarks

status only quotes measured numbers: a miner that started a moment ago says warming up instead of showing the previous run's hashrate, because the dataset takes 15–25 seconds to build.

Anything that fails has a row in when something is wrong.

Updating​

RouteCommandWhat survives
A. One commandsudo ./oneclick.sh updateconfig, service, tuning; the binary is rebuilt
B. Containerdocker run --rm ghcr.io/molik-labs/zmrig update --check, then pull and recreatenothing inside the container — that is the point
C. Image, live stickzmrig-os update --applyuntil reboot; a live stick is read-only by design
C. Image, installedzmrig-os update --applythe change lands on the disk and stays

update --check exits 0 when the image is current, 3 when a newer one is published and 2 when it cannot tell — which is what the update timer reads.

The 3 % fee, and how to audit it​

The Zig engine spends 3 % of Monero mining time on the developer's wallet. The C++ engine takes nothing. The fee is written into the config explicitly rather than implied, and there are three independent ways to check it — none of which requires trusting this page:

zmrig --check | grep donate        # what this rig will actually do
sudo ./oneclick.sh verify          # the installer's own audit
./scripts/verify-fee.sh --source-only   # the constants, straight from the source

The last one reads fee.default_percent out of zmrig/src/fee.zig and fails if any page in this repository disagrees with it, including the page you are reading.

To change it, say so where the config is written:

sudo ./oneclick.sh config --donate-level 0     # this rig, no fee
docker run -e DONATE=0 ...                     # the container
zmrig-os setup --donate 0                      # the appliance

11 is refused, and so is a word: the miner only accepts 0..10, and a value it rejects would be found at boot instead of at setup. The fee page has the per-rate table and the exact code that implements it.

More than one rig​

Every rig needs its own name, or the pool dashboard shows one machine doing arithmetic that does not add up:

sudo ./oneclick.sh install --wallet 4... --rig-id rig-02   # route A
docker run -e WORKER=rig-02 ...                            # route B
zmrig-os setup --wallet 4... --worker rig-02               # route C

Then, if you want them in one place: zmrig-os id prints the Device ID to enrol, and zmrig-os fleet --url https://your-fleet points the rig at a Telegram bot. The control plane is a whole fleet; the installer has a loop for ten machines in unattended installs.

The full table, with the log lines that identify each one, is in troubleshooting.

Where these numbers come from​

Nothing on this page is quoted from memory. The commands are checked against the scripts that implement them and the fee against the constant in the source, by tests/docs/setup-page.sh, so a renamed subcommand fails a test instead of failing your terminal. Where a number cannot be measured in this environment it is not printed at all — see how this repository is tested.
